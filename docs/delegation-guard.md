# Standalone delegation prerequisite guard

> Archived, unaccepted candidate. Local tests passed, but the native Code Local Agent request was rejected by the strict input schema. An independent negative test also found missing signed failure receipts. Investigation stopped at its bounded attempt limit. This candidate was not globally deployed; the accepted prerequisite-only guard remains installed. No production routing or QA enforcement is certified here.

The standalone guard adds a separate `PreToolUse` handler for native `Agent` and `spawn_agent` calls beside an already installed legacy workflow core. It leaves the selected core files and unrelated hook groups untouched. The guard requires matching native session/turn identifiers, a protected project root, a valid frozen substantial plan, and an active task state. An unplanned delegation is denied until a substantial plan is saved through the existing workflow interface.

Install it with an explicit trusted core directory:

```sh
python3 -B tools/configure_delegation.py --platform codex --core-dir "$HOME/.codex/workflow-hooks-kit/bin"
python3 -B tools/configure_delegation.py --platform claude --core-dir "$HOME/.claude/workflow-hooks-kit/bin"
```

Claude can opt into mandatory frozen-stage packet delivery by supplying a trusted model policy:

```sh
python3 -B tools/configure_delegation.py --platform claude --core-dir "$HOME/.claude/workflow-hooks-kit/bin" --model-map /secure/path/model-policy.json
```

The policy is an owner-only regular file of at most 8 KiB, with exactly this shape: `{"schema":1,"models":{"alias":"exact-native-model-id"}}`. Schema must be integer `1`; there must be 1–16 aliases, each alias and native ID bounded printable ASCII with no whitespace or control characters. Duplicate JSON keys, symlinks, FIFOs, foreign-owned or group/world-readable files are rejected before installation changes. The installer copies the exact validated bytes to private `bin/delegation-guard/model-policy.json` and registers that owned path. It also copies the shared `delegation_binding.py` helper. Supplying `--model-map` for Codex fails before config or runtime changes because this tested input-rewrite contract is Claude-specific.

With strict mode enabled, the guard first runs the existing prerequisite check, reloads the matching active ledger, and accepts only the exact Claude `Agent` input fields `description`, `prompt`, `model`, and `subagent_type`. A single-stage ledger selects its only stage deterministically and replaces the description with `[workflow-stage:N] <exact stage name>`. A multi-stage ledger requires that exact selector in the original description. The model alias must exactly equal the frozen stage's `worker_model` and resolve through the trusted map; no fallback or alias guessing occurs. The original prompt is accepted only as bounded valid UTF-8 text up to 32 KiB, then replaced with the canonical packet from `delegation_binding.py`. The result returns `updatedInput` without an explicit permission approval, leaving native approval handling to Claude. It also requires a valid native `tool_use_id`; only its SHA-256 digest is included in the receipt version binding.

Strict receipts bind the guard, prerequisite gate, receipt helper, trusted legacy core/workflow bytes, binder bytes, exact model-policy bytes, the canonical seven-field stage binding, and the hashed native tool-use identity. They contain no original prompt, raw tool-use ID, native model ID, or alias mapping. They still record only that the hook emitted the rewritten packet. They do not prove a child started, ran, followed the packet, completed, or passed QA. The separate observer remains unwired to this request binding, and the companion PreToolUse guard cannot safely veto legacy QA persistence. Do not claim completion or QA enforcement from this integration.

Without `--model-map`, the prior prerequisite-only behavior remains. On reruns, an already-owned strict install stays strict even when the option is omitted; an edited owned policy is preserved and the installer refuses replacement. Uninstall needs no source policy file and removes only unchanged files created by this installer, preserving later edits. Upgrading a prior three-file prerequisite install adds the binder and replaces only its exact owned Claude handler while preserving foreign handlers.

The installer copies `delegation_gate.py`, `delegation_guard.py`, `hook_receipt.py`, and `delegation_binding.py` into a private `bin/delegation-guard/` directory, keeping other kit helpers independently owned. In strict mode it also copies the owner-only model policy. Receipts are kept in the owner-only `delegation-receipts/` state directory. Each marker records that the prerequisite check ran for the named native IDs; it does not mean a worker started or finished. The runtime digest covers the guard, gate, receipt helper, and selected legacy core/workflow bytes; strict receipts additionally bind the binder, policy, and validated request version. Reruns are idempotent. Use `--uninstall` with the same platform and core directory to remove only the unchanged owned handler and unchanged files created by this installer. Receipt history and backups remain available. If an owned command or runtime was changed, the installer preserves it and refuses replacement/removal. An exact duplicate companion command or a selected core that already contains the gate causes installation to stop. Unrelated observer matchers are preserved alongside the gate.

When no ledger exists, the gate denies delegation without creating a ledger or other workflow record. Save a substantial plan through the existing `workflow-ledger plan '<JSON>'` interface, then retry. This keeps the gate read-only and allows the established planner to create a complete in-progress plan.

This is a prerequisite gate. It cannot authenticate that a payload came from the native host, prove a worker actually started, verify model identity, or certify completion or review. Existing observer hooks may match the same delegation events and run alongside this gate; their presence does not establish that a worker started. A local replay may exercise the check but is not evidence of native dispatch. Local tests and native activation are separate evidence.

Deployment proceeds in phases: (1) Codex and Claude Code gates plus native acceptance; (2) ordinary GPT capability assessment and implementation if supported; (3) Cowork. Evidence from the first phase does not certify later phases.

The dedicated executable rejects unreadable, oversized, non-object, or missing/invalid event and tool identities with a denial and no fabricated receipt. An explicitly identified unrelated tool remains a no-op. This does not compensate for a native host that never invokes the handler. A native Code Local negative sample observed one denied unprepared Agent call, no child result, no workflow ledger creation, and no corrective Stop turn. A repeated fresh first-prompt test of the current installed guard matched its single signed failure receipt to the exact native session ID from Desktop status and the raw prompt ID from separate legacy event metadata, verified the current runtime digest, and consumed the marker once. Neither a task ledger nor a Stop-continuation marker existed for that native turn. Positive native dispatch, actual model binding and Codex activation remain separate acceptance requirements.
