התקן שערי שמירה במצב file-tools ל־Codex בלבד לפי `docs/customer-install.md`. עבוד מעותק התצוגה הקפוא של המאגר `https://github.com/omerm-AI/workflow-hooks-kit`, בתג `hygiene-file-tools-preview-2026-10-20`. המחשב צריך macOS/Linux ו־Python 3.9 ומעלה.

ההתקנה אינה משנה קבצי פרויקט ואינה מבצעת ניקוי גורף בדיעבד. ההגנה חלה על פעולות עתידיות נתמכות בתיקיות חדשות וקיימות.

1. בצע בפועל: `git clone --branch hygiene-file-tools-preview-2026-10-20 --depth 1 https://github.com/omerm-AI/workflow-hooks-kit.git workflow-hooks-kit-preview`, היכנס לתיקייה, ודא `git describe --tags --exact-match HEAD` מחזיר את התג ו־`git status --short` נקי. קרא את `README.md`, `install.py`, `docs/hygiene-enforcement.md`, `docs/hook-status.md` ו־`docs/acceptance/2026-10-20-hygiene.md`. אל תשתמש ב־fork, ענף אחר או עותק ששונה.
2. בדוק בחשבון Codex אם כבר יש kit, plugin או core מותאם מקביל, או runtime אחר שתופס אותם אירועי hooks. אם יש התנגשות, עצור והצג נתיבים וצעד בטוח. אל תיצור כפילות, תדרוס, תסיר או תמזג runtime אחר.
3. הרץ בדיקת עשן ללא מודל עם נתיב מוחלט חדש שעדיין לא קיים. אל תיצור את התיקייה מראש. לדוגמה: `python3 tools/hygiene_smoke.py --home /absolute/new/codex-smoke-home --platform codex --hygiene-mode file-tools`. הבדיקה צריכה לעבור על coexistence, התקנה חוזרת, שערים והסרת רישום זמני. אם הבית קיים, הקובץ חסר או הבדיקה לא עוברת, עצור ודווח.
4. לפני הפעלת הפרופיל, בחר נתיב מוחלט שני שטרם קיים, נפרד מבדיקת העשן, והתקן בו בפועל: `python3 install.py --platform codex --home /absolute/new/codex-native-home --hygiene-file-tools`. בדוק שנוצרו ארבע הגדרות ההוק ושהמתקין לא שינה קבצי פרויקט. רק אחרי ההתקנה הרץ `CODEX_HOME=/absolute/new/codex-native-home/.codex codex login status`. אם אינו מחובר, בקש ממני להשלים כניסת מנוי רגילה באמצעות `CODEX_HOME=/absolute/new/codex-native-home/.codex codex login`, בלי מפתח API ובלי להעתיק credentials. הפעל `CODEX_HOME=/absolute/new/codex-native-home/.codex codex -C /path/to/disposable-project`. בתוך הפרופיל פתח `/hooks` ובקש אישור אמון לארבע ההגדרות שנבדקו. גילוי ארבעת ההוקים בפרופיל הוכח ללא מודל; canary נייטיבי בפרופיל החדש עדיין דורש כניסה, אמון וראיות בפועל. אל תתחיל inference כשהפרופיל אינו מחובר או ההוקים אינם מהימנים.
5. בצע canary בפרויקט זמני בלבד ואמת אירוע native, מקור ההוק ותוצאת קובץ בפועל. מסלול הפרופיל זוהה ללא מודל; הבדיקה הנייטיבית עצמה עדיין **Open** עד כניסה, אישור אמון ותוצאה מוכחת. אין להחשיב זיכרון, סירוב מילולי של המודל או קובץ הגדרות כראיית חסימה בקוד.
6. השתמש רק בהתחברות המנוי הקיימת של לקוח Codex. אין להשתמש במפתח API שסופק, להעתיק קובצי credentials או לבצע fallback ל־API או לשירות בתשלום. אם אין התחברות מנוי פעילה, עצור והצג את שלב הכניסה.
7. בדוק managed settings ודריסות ברמת פרויקט. אל תניח שסשנים שכבר פתוחים טוענים הגדרות חדשות; בדוק בנפרד או דווח **Open**. אל תתקין בחשבון האמיתי לפני שעשן, התקנת הבית השני ו־canary native הצליחו בגבול הנבדק.
8. אחרי canary מצליח, התקן לחשבון Codex בלבד: `python3 install.py --platform codex --hygiene-file-tools`. מצב file-tools אוכף רק שמירות בכלי קבצים native מוכרים וסיום משימה. כתיבה דרך shell או מחברים אחרים אינה מכוסה; אין להציגו כאכיפה על כל נתיב כתיבה. הסבר את ההשפעה והיקף הראיות לפני ההתקנה. בקשתי המפורשת להתקין מאשרת את opt-in. בדוק את נתיבי ההתקנה ושימור הגדרות זרות.
9. המתקין מתקין `WORK_STANDARDS.md` בתיקיית kit, אך לא עורך `AGENTS.md`/הוראות פרויקט ולא טוען אוטומטית את `rules/HYGIENE-CODEX.md`. בעבודות קבצים עתידיות הורֵה לסוכן לקרוא את שני מסמכי המדיניות, או הוסף הפניה מבוקרת להוראות הפרויקט. אל תסתמך על memory. כש־hook חוסם כלי נתמך, קרא את הודעתו והמשך לפי ה־ledger או ה־hygiene sentinel המדויק שהיא מחזירה.
10. בהמשך השתמש רק ב־`workflow-ledger plan`, `workflow-ledger qa` וב־`workflow-hygiene inspect`, `read`, `review`, `restore` כפקודות standalone דרך shell native שמחובר ל־hook. ערוך בכלי קבצים native מוכר אחרי review של הנתיב המדויק. לפני שינוי קובץ קיים גבה לתיקייה ייחודית תחת `Old/YYYY-MM/` באותו פרויקט ושמור נתיב יחסי ו־hash מאומת; לקובץ חדש אין גרסה קודמת. סיים review ו־QA אחרי כל עריכה. השאר מקורות ותלויות נדרשים במיקום הפרויקט; עזרים אחרים ב־`Assets`. העבר לארכיון רק כפילות byte-for-byte של מדיה או מסמך נתמך, עם עותק קנוני נפרד ובדיקת הפניות. אם יש ספק, שמור ושאל. אין מחיקה לצמיתות או שינוי אוטומטי של תיקיות לא קשורות.
11. דווח על commit, פלט smoke, התקנת הבית השני, ראיית trust/callback/canary והאם הותקן החשבון. סמן **Tested and proven** רק למה שנצפה ו־**Open** לפערים. פריסה גלובלית אינה מוכחת. הקובץ `docs/customer-install.md` מפרט את מגבלות הכיסוי וה־uninstall, שמשאיר runtime וגיבויים לשחזור; אל תבטיח 100%.

בדיקות בטוחות: במק בלבד, השתמש ב־`workflow-hygiene check` עם JSON הכולל `argv` ו־`timeout` של 1–3 שניות. זו הרצה ללא shell, ללא ילדים ורשת, כשהפרויקט לקריאה בלבד וכתיבה מותרת רק לאזור זמני פרטי. בדיקת תהליך אינה מאשרת review או QA. בדיקות ארוכות, builds שיוצרים ילדים ופלטפורמות אחרות אינם נתמכים במסלול זה; אל תעקוף חסימה ואל תפעיל פריסה גלובלית עבור הלקוח בלי בדיקה מתאימה. קרא `docs/acceptance/2026-10-20-safe-check.md`.

היקף חובה: file-tools הוא המצב החלקי שנבחר כאן, ולא מצב enforce הקפדני. פקודות shell וכלים לא מוכרים שומרים על התנהגות הבסיס ועלולים לכתוב ללא שער הניקיון. פתח כל פרויקט בתיקיית העבודה המדויקת שלו. תיקייה קיימת אינה סשן שכבר פועל: יש לאמת בנפרד סשן חי ישן וסשן חדש. התקנה אינה מנקה קבצים היסטוריים. קרא `docs/hygiene-customer-status.md`, והריץ `python3 tools/hygiene_cleanup_smoke.py --platform both --hygiene-mode file-tools --home /absolute/new/cleanup-proof-home` להדגמה מבודדת; זו בדיקת פקודות הוק מותקנות, לא סשן native ולא ניקוי הפרויקטים האמיתיים.

הוכחה קודמת מחשבון המפעיל או מתצוגת strict אינה מחליפה בדיקת canary במצב file-tools בפרופיל הלקוח שמתקינים כעת. קרא גם `docs/acceptance/2026-10-20-file-tools.md`; הפרד בין חשבון קיים, פרופיל לקוח חדש וסשן שכבר טען הוקים.
